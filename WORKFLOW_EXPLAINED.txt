��� 4 DATABASE TABLES

1. PROFILES TABLE
   ├─ Stores: User account information
   ├─ Fields: id, email, name, avatar_url, gender
   ├─ Created by: Signup process
   └─ Example row:
       id: "550e8400-e29b..."
       email: "john@example.com"
       name: "John Doe"
       gender: "male"

2. POSTS TABLE
   ├─ Stores: Lost/Found item listings
   ├─ Fields: id, user_id, title, description, type, category, 
   │          image_url, location_lat, location_lng, contact_info
   ├─ Created by: Users creating posts
   └─ Example row:
       id: "660e8400-e29b..."
       user_id: "550e8400-e29b..."  (foreign key → profiles)
       title: "Lost Black Wallet"
       type: "lost"
       category: "Valuables"
       location_lat: 28.6139
       location_lng: 77.2090

3. CONVERSATIONS TABLE
   ├─ Stores: Chat threads between users
   ├─ Fields: id, user_1_id, user_2_id, post_id
   ├─ Created by: Users starting chat
   └─ Example row:
       id: "770e8400-e29b..."
       user_1_id: "550e8400-e29b..."  (foreign key → profiles)
       user_2_id: "880e8400-e29b..."  (foreign key → profiles)
       post_id: "660e8400-e29b..."   (foreign key → posts)

4. MESSAGES TABLE
   ├─ Stores: Individual chat messages
   ├─ Fields: id, conversation_id, sender_id, content, created_at
   ├─ Created by: Users sending messages
   └─ Example row:
       id: "990e8400-e29b..."
       conversation_id: "770e8400-e29b..."  (foreign key → conversations)
       sender_id: "550e8400-e29b..."        (foreign key → profiles)
       content: "Hi, is this still available?"
       created_at: "2025-02-04T10:30:00Z"

��� ROW LEVEL SECURITY (RLS) - Data Protection

RLS is like a bouncer at a club - only the right people get in!

┌──────────────────────────────────────────────────────────────┐
│ profiles TABLE                                               │
├──────────────────────────────────────────────────────────────┤
│ SELECT: ✓ Anyone can read (public profiles)                 │
│ INSERT: ✓ Users can create their own profile                │
│ UPDATE: ✓ Users can only update THEIR profile               │
│ DELETE: ✓ Users can only delete their own profile           │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ posts TABLE                                                  │
├──────────────────────────────────────────────────────────────┤
│ SELECT: ✓ Anyone can read (public posts)                    │
│ INSERT: ✓ Users can create posts (auth.uid() = user_id)     │
│ UPDATE: ✓ Users can only update THEIR posts                 │
│ DELETE: ✓ Users can only delete THEIR posts                 │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ conversations TABLE                                          │
├──────────────────────────────────────────────────────────────┤
│ SELECT: ✓ Users can only see conversations they're in       │
│ INSERT: ✓ Users can create conversations they're part of    │
│ UPDATE: ✓ Users can only update their conversations         │
│ DELETE: ✓ Users can only delete their conversations         │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ messages TABLE                                               │
├──────────────────────────────────────────────────────────────┤
│ SELECT: ✓ Users can only see messages from their chats      │
│ INSERT: ✓ Users can only send their own messages            │
│ UPDATE: ✗ No one can update messages (immutable)            │
│ DELETE: ✓ Users can only delete their own messages          │
└──────────────────────────────────────────────────────────────┘

- Generates 6-digit OTP

- Returns success

      ↓

User receives email with OTP, enters code in app

      ↓

    name: "John Doe",

    gender: "male"
  })

      ↓

Database checks RLS:
- Is user authenticated? ✓
- Does auth.uid() match the id being inserted? ✓
- All fields valid? ✓

      ↓

INSERT succeeds, new row in profiles table:

��� RELATIONSHIPS (Foreign Keys)

    profiles
        ↑
        │ id
        │
    posts
        │ user_id → profiles.id
        │
    conversations
        ├─ user_1_id → profiles.id
        ├─ user_2_id → profiles.id
        └─ post_id → posts.id
            │
        messages
            ├─ conversation_id → conversations.id
            ├─ sender_id → profiles.id

This means:
- If user deleted, all their posts/messages deleted too (CASCADE)
- If post deleted, all conversations about it deleted
- If conversation deleted, all messages in it deleted

��� KEY CONCEPTS

1. AUTHENTICATION
   - Email/Password: Users sign up and login
   - OTP: Email verification for extra security
   - Session: User stays logged in

2. AUTHORIZATION
   - RLS ensures users can only access their own data
   - Database enforces rules automatically
   - No changes needed in frontend code

3. REAL-TIME
   - Subscriptions let frontend listen for database changes
   - When anyone creates post/message, everyone sees it instantly
   - Socket connection stays open

4. STORAGE
   - All data persisted in PostgreSQL database
   - Automatic backups by Supabase
   - No data lost if frontend crashes

✅ SUMMARY

Your Supabase workflow:

1. Frontend sends request (e.g., "create post")
2. Service processes it (e.g., PostService)
3. Supabase client sends to Supabase backend
4. Database executes query
5. RLS policies check permissions
6. If allowed, operation succeeds
7. Result returned to frontend
8. Frontend updates UI

Everything is connected automatically - no glue code needed!

You just need:
✓ Database tables (run SQL)
✓ Environment variables (.env.local)
✓ Frontend running (npm run dev)
